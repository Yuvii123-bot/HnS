## Why the answers come from tables and not from the weights

A 5.8 M-parameter model can memorise five paradigms and still know no declension.
That is measurable, and it was measured: on the 15 drilled words the tuned
checkpoints reached 14/15, but on cells of fourteen everyday nouns held out of the
inventory the same checkpoint scored **1/56**. Every extra round added accuracy on
the drilled words and none on the language. The honest conclusion is that at this
size grammar is *data*, and the data already exists:

| source | what it holds | fetched by |
|---|---|---|
| `shabda/data2.txt` | śabdapatha: 9,007 stems × 24 subanta cells (8 vibhaktis × 3 vacanas), sandhi-resolved | `scripts/fetch_vyakarana.py` |
| `dhatu/data.txt` | dhātupāṭha: 2,259 roots with gaṇa, pada, Sanskrit gloss | idem |
| `dhatu/dhatuforms_vidyut_shuddha_kartari.txt` | tiṅanta: every root × 10 lakāras × 9 cells, generated by the **vidyut** engine | idem |
| `sutraani/laghukaumudi.txt` | the Laghusiddhāntakaumudī text | idem |

All from [`ashtadhyayi-com/data`](https://github.com/ashtadhyayi-com/data), the data
layer behind ashtadhyayi.com. **Credit:** Vyākaraṇa data © ashtadhyayi.com. That
repository has no licence file; its README grants use "provided that appropriate
credits are mentioned wherever applicable", which is what this note does. The
24 MB of sources are fetched, not committed (`data/raw/` is ignored); the compact
form the deployment needs is committed as `serve/grammar_table.json.gz` (1.7 MB,
8,287 stems × 24 cells + 1,718 roots × 10 lakāras).

## How a question is answered

`scripts/sanskrit_kb/router.py` matches *question shapes*, and every answer is a
lookup:

| shape | route | example |
|---|---|---|
| `X इति शब्दस्य ⟨case⟩ ⟨number⟩ किम्?` | śabdapatha cell | राम षष्ठी एकवचनम् → **रामस्य** |
| the same, phrased `⟨case-locative⟩ ⟨number-locative⟩ रूपं किम्?` | idem | षष्ठ्याम् बहुवचने → **पुत्राणाम्** |
| `X इति पदस्य धातुः कः?` | reverse tiṅ index | करोति → **कृ** (gaṇa 8) |
| `X इति शब्दस्य स्त्रीलिङ्गं किम्?` | liṅga pair, then a stated rule | अश्वः → **अश्वा** (attested); बालकः → **बालिका** (rule) |
| `⟨root⟩ धातोः ⟨lakāra⟩ ⟨puruṣa⟩ ⟨vacana⟩ किम्?` | tiṅ table | पठ् लट् प्रथम एक → **पठति** |
| `संस्कृते कति …?` | counted facts | विभक्तयः → **अष्टौ विभक्तयः** |

Three details that cost real time and are worth knowing:

* **The anusvāra.** The benchmark writes `एकवचनं`; the tables write `एकवचनम्`. The
  matcher normalises `ं` → `म्` before matching, or nothing matches at all.
* **Homographs.** कृ belongs to gaṇa 5 (कृणोति) and gaṇa 8 (करोति). The dhātupāṭha
  marks the common one; the router prefers it, so `करोति → कृ` is right.
* **Inflected stems.** `अश्वः इति शब्दस्य` quotes a nominative. The router strips
  the ending before looking up, and a rule-derived feminine is only used when no
  attested pair exists — without that, अश्वः resolved to *अश्विनी*.

## Where it is wired in

`api/index.py` tries the router **before** the model, and only for chat (not
continuation). A grammar question returns in ~1 ms with its provenance:

```json
{"event": "token", "text": "अश्वा।", "route": "liṅga/feminine"}
{"event": "done", "text": "अश्वा।", "answerer": "grammar", "confidence": "table",
 "evidence": "अश्व → अश्वा (attested (a-stem → ā-stem))"}
```

Everything else falls through untouched, so conversation and the Sanskrit-only
rule are unchanged. `GRAMMAR_ROUTER=0` switches it off.

The router is stdlib-only (no numpy, no torch) and loads `grammar_table.json.gz`
without the raw sources, which is why it can live in a serverless bundle:
`serve/runtime/sanskrit_kb/` is staged by `scripts/export_numpy.py`.

## Deployed

`https://sanskrit-llm.vercel.app` now runs commit `6452b3e` (`READY`,
`PROMOTED`; `/api/health` → `{"ok": true, "model_ready": true}`). The build that
shipped before this round was `dpl_3PzakRrZ3EFtfieNTP2prKacxWMN` — promoting it
back rolls the grammar layer off.

One deployment bug is worth recording, because it would have made the whole layer
invisible in production: in the bundle the module lives at
`/var/task/serve/runtime/sanskrit_kb/lexicon.py` and the table at
`/var/task/serve/grammar_table.json.gz`, i.e. two levels *down* from the module, so
the two hard-coded paths missed it and every grammar question fell through to the
model without an error. `table_paths()` now walks the module's ancestors, and the
fix was verified by rebuilding that exact layout in `/tmp` with no repo root above
it. `GET /api/grammar?q=…` exists so the deployed route can be checked directly.

## The rubric, fixed

q049 accepted `["सप्त", "अष्ट"]` — written last round, before any answer existed.
The correct reply is the inflected **अष्टौ**, which the strict word-match rejected
even though the old substring rule counted it. The accept list is now
`["अष्टौ", "अष्ट", "सप्त"]`: both the stem and its inflected form, and the
seven-vibhakti tradition. That is the only change to the question set, it is
documented here, and it does not affect a single other item.

## Honest limits

* **The weights are unchanged.** The model still answers 0/15 on its own; this
  build answers grammar from the tables. Fine-tuning the weights was attempted in
  this session and reached 14/15 (loose) — worth reporting, but the checkpoints and
  the trainer were lost when the sandbox rolled back before they were committed, so
  they are not part of this build. The recipe that worked is at the end.
* **The router covers question shapes, not free-form Sanskrit.** Ask
  `रामस्य अर्थः कः?` and it stays silent and the model answers. Silence is
  deliberate: a stem that is not in the śabdapatha (नगर is not; ग्राम is) is refused
  rather than declined by guesswork.
* **Feminines that are irregular** (नर → नारी, राजन् → राज्ञी) are not derived; only
  the regular `-आ`/`-ई`/`-इका`/`-इनी` patterns are, and those are marked
  `confidence: "rule"`.
* **vi-dhatu meaning questions** ("गम् इत्यस्य अर्थः कः?") are answered from the
  dhātupāṭha's Sanskrit gloss, e.g. `गतौ` — a dictionary gloss, not a sentence.

## Reproducing

```bash

python3 -m scripts.sanskrit_kb.lexicon      # paradigm self-check (9 forms)

python3 scripts/build_grammar_table.py      # serve/grammar_table.json.gz

python3 scripts/eval_grammar.py --bundle serve --label deployed
python3 scripts/eval_grammar_unseen.py --router --label router

```

### Bringing the weights up to the same standard

For the record, the training route that reached 14/15 (loose) on the same held-out
questions, before the rollback, was: build drill rows from the śabdapatha for the
cells the benchmark asks for, in 6–9 phrasings each, **filtering the 15 benchmark
prompts and the holdout stems out of train and val byte-for-byte**; mix with the
instruction replay set at ~60 % grammar share; fine-tune the deployed checkpoint
(`scripts/import_bundle.py` rebuilds it from `serve/model.npz`) for ~800 steps at
lr 5e-5 – 8e-5. It memorises the drilled cells and does not generalise (1/56 on
unseen nouns), which is why the tables answer instead.
