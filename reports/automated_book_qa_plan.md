# Experimental automated books and Q&A training

This is a separate GitHub Actions candidate, not a production deployment. It begins from `authored-qa-seed-44247588156.pt` (weights and optimizer), whose prior nominal base plus non-padding positions is approximately 220,579,586. The prior book checkpoint and production deployment remain intact.

The mix is prepared from five Amarahasa books (manifest-verified original-site IAST converted automatically to Devanagari), the 228 agent-authored QA drafts, and SktQA's Ramayana benchmark. Only single-answer, no-multiple-choice SktQA rows are included; Ayurveda entries are excluded. QA questions receive assistant-only loss. Book text receives language-model loss. Every item has its own attention context; no training examples are concatenated. Each draw selects QA with probability 0.75 and book text with probability 0.25. This is a small experimental corpus and will be sampled repeatedly, not a source of unique token counts.

None of this establishes data accuracy or grammar retention. Devanagari transliterations and authored pairs are not independently reviewed. Amarahasa states CC0 unless otherwise noted but book-specific terms need confirmation; the SktQA repository declares Apache 2.0, while data-specific and underlying rights still require verification. SktQA is a published benchmark and must not be used as held-out evaluation for this candidate. Existing evaluation sets have known overlap; the independent 250-question comparison remains unfinished. Do not deploy based on this run alone.

The first run targets 2,000 steps at batch 8 with optimizer, Python RNG and Torch RNG, dataset fingerprint, actual nonpadding token counts and SHA-256 recorded. Every 250 steps the workflow publishes a uniquely named checkpoint plus checksum and metadata to the existing release. The run is bounded rather than endless to limit repeated-data overfitting; there is no automatic 250M-token or 500-question success claim. A workflow-dispatch input can resume a verified published `book-qa-auto-...pt` checkpoint to a specified higher step; it refuses to resume if the data fingerprint changes. An interrupted job can lose work since its last completed checkpoint upload.
